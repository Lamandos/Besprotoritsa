# Сетевая спецификация кооперативной игры

## Статус и область действия

Этот документ задаёт нормативный протокол онлайновой партии для 2–4 игроков.
Правила, типы и терминология игры определены в [спецификации правил](rules-spec.md)
и [глоссарии](glossary.md). Транспорт — WebSocket с сообщениями JSON-RPC 2.0;
двоичная Protobuf-реализация может использовать те же поля и семантику.

Сервер является единственным источником истины. Он хранит полный `GameState`,
выполняет `validate` и `step`, бросает кубики, меняет колоды, разрешает
автоматические эффекты и назначает следующий номер состояния. Клиент отображает
полученное состояние и формирует намерение игрока; он не вычисляет результат
правил, не выбирает случайность и не предсказывает скрытые данные.

Слова «должен» и «нельзя» в этом документе означают обязательные требования.

## Идентичность, комната и версии

Перед вызовами клиент проходит аутентификацию в WebSocket-рукопожатии. Сервер
выдаёт непрозрачный `sessionToken` и, при входе в комнату, непрозрачный
`resumeToken`. Токены не являются `playerId`, не передаются другим клиентам и не
попадают в журналы. Повторное подключение использует именно `resumeToken`.

`roomId`, `playerId`, `heroId`, `commandId` и идентификаторы сущностей — строки.
Код приглашения комнаты должен быть криптографически непредсказуемым и иметь не
менее 128 бит энтропии; короткие перебираемые коды не допускаются.
`commandId` — UUID, сгенерированный клиентом. `stateVersion` — неотрицательное
целое, монотонное для комнаты. Новая партия начинается с `stateVersion: 0`.

Комната проходит состояния `lobby`, `starting`, `inGame`, `completed`. В `lobby`
могут быть 2–4 участника; смена героя и готовность доступны только там. Создатель
комнаты является её `host`, но не получает прав менять правила или чужое состояние.
Партия стартует, когда в комнате 2–4 игрока, все выбрали разные допустимые герои и
все отправили `PlayerReady(ready: true)`.

## Конверт сообщений

Клиентские вызовы — JSON-RPC requests, например:

```json
{
  "jsonrpc": "2.0",
  "id": "rpc-018",
  "method": "SendCommand",
  "params": { "roomId": "r-7f", "commandId": "8a0c2d9e-0db4-4a8c-b982-91306c02e35c", "expectedStateVersion": 12, "command": { "type": "move", "target": { "q": 0, "r": 1 } } }
}
```

Серверские изменения — JSON-RPC notifications с теми же `method` и `params`;
у них нет поля `id`. Ответ на успешно принятый запрос содержит только
`{"accepted": true, "commandId": "…"}`. Он не заменяет `StateUpdate`.
Ошибка уровня JSON-RPC (неверный JSON, неизвестный метод, неверные типы) имеет
стандартный объект `error`; ошибка игровой команды всегда приходит отдельным
`RejectionNotice`.

Все строки на проводе — UTF-8, числа — JSON numbers. Неизвестные обязательные
поля и неверные значения отклоняются. Неизвестные необязательные поля должны
игнорироваться для прямой совместимости. `protocolVersion` во всех сообщениях
ниже обязателен и сейчас равен `1`; несовместимая версия закрывает соединение с
JSON-RPC ошибкой `unsupported_protocol_version`.

## Сообщения лобби

### `CreateRoom`

Создаёт комнату и добавляет вызывающего как первого участника.

```json
{
  "protocolVersion": 1,
  "requestId": "create-01",
  "contentSetId": "mvp",
  "maxPlayers": 4,
  "visibility": "private"
}
```

`maxPlayers` может быть только `2`, `3` или `4`. В ответе сервер возвращает
`roomId`, роль `host`, `playerId`, `resumeToken`, `stateVersion: 0` и снимок
состояния лобби. Пароль, код приглашения и параметры сидирования не выдаются
клиенту как часть состояния игры.

### `JoinRoom`

Входит в лобби или восстанавливает участника после разрыва:

```json
{
  "protocolVersion": 1,
  "roomId": "r-7f",
  "inviteCode": "optional-private-code",
  "resumeToken": "present-only-for-reconnect"
}
```

Первичный вход возможен только в `lobby` и при наличии свободного места. При
`resumeToken` сервер сопоставляет именно прежнего `playerId`, заменяет его старое
соединение и немедленно отправляет этому соединению полный `StateUpdate`.
Ни `playerId`, ни отображаемое имя нельзя использовать для захвата чужого места.

### `SelectHero`

```json
{
  "protocolVersion": 1,
  "roomId": "r-7f",
  "heroId": "engineer",
  "expectedStateVersion": 3
}
```

Выбор доступен только самому участнику в `lobby`. Сервер проверяет наличие героя,
его уникальность и версию, увеличивает `stateVersion` и рассылает `StateUpdate`
всем игрокам комнаты.

### `PlayerReady`

```json
{
  "protocolVersion": 1,
  "roomId": "r-7f",
  "ready": true,
  "expectedStateVersion": 4
}
```

Сервер снимает готовность игрока при смене его героя, при входе/выходе участника
и при любом изменении состава лобби. Когда последнее условие старта выполнено,
сервер единожды создаёт полный `GameState`, переводит комнату в `inGame` и
рассылает персональные снимки с новой версией.

## Игровая команда

### `SendCommand`

Все намерения, влияющие на партию, идут одним сообщением:

```json
{
  "protocolVersion": 1,
  "roomId": "r-7f",
  "commandId": "8a0c2d9e-0db4-4a8c-b982-91306c02e35c",
  "expectedStateVersion": 12,
  "command": {
    "type": "resolvePendingDecision",
    "choice": { "type": "eventOption", "optionId": "investigate" }
  }
}
```

`command` — tagged union, точно отображающий публичные варианты `GameCommand`:
`move`, `airlockMove`, `closeCorridor`, `attack`, `skillCheck`,
`resolvePendingDecision`, `endTurn`, `equip`, `unequip`,
`implantModification`, `useTerminal`, `depositIntoChest`, `withdrawFromChest` и
`exchange`. Поля вариантов повторяют поля соответствующего типа ядра:
например, `move.target` — `HexCoord`, `attack.targetInstanceId` — идентификатор
монстра, а `exchange` содержит получателя и конкретные передаваемые карты/кредиты.
Клиент не посылает результат броска, новую карту, лечение, состояние колоды,
урон или какой-либо производный эффект. `HealCommand` и `ReceiveCardCommand` —
внутренние переходы эффектов сервера; их присутствие в модели правил не делает
их командами сетевого клиента.

Команда обрабатывается сервером последовательно в критической секции комнаты:

1. Сервер аутентифицирует соединение, проверяет участие, контролёра героя и
   допустимость команды в текущей фазе. Для `PendingDecision` контролёром
   является владелец именно этого решения, а не обязательно текущий активный
   герой.
2. Если `expectedStateVersion` не равен текущей версии, команда не выполняется.
3. Сервер проверяет форму команды, применяет правила к полному `GameState` и
   завершает все обязательные автоматические переходы до стабильной точки либо до
   разрешённого `PendingDecision`.
4. При успехе сервер атомарно сохраняет новое полное состояние и увеличивает
   `stateVersion` ровно на один, независимо от числа внутренних эффектов.
5. Сервер отправляет по одному персональному `StateUpdate` каждому действующему
   соединению комнаты.

В каждой комнате сервер хранит журнал дедупликации как минимум до завершения
партии: ключ `(playerId, commandId)`, криптографический хеш команды и итог
(`accepted` или код отказа). Повтор того же ключа с тем же хешем возвращает
сохранённый итог и **не** выполняет редьюсер второй раз. Тот же ключ с другим
хешем отклоняется как `command_id_reused`. При потере ответа клиент повторяет
исходный байтово эквивалентный `SendCommand` с тем же `commandId`, а не создаёт
второе намерение.

## Снимок состояния и защита от мапхака

### `StateUpdate`

Начальная синхронизация, принятая команда, переподключение и изменение лобби
передаются единым полным снимком, а не дельтой:

```json
{
  "protocolVersion": 1,
  "roomId": "r-7f",
  "stateVersion": 13,
  "reason": "commandApplied",
  "acceptedCommandId": "8a0c2d9e-0db4-4a8c-b982-91306c02e35c",
  "serverTime": "2026-09-20T12:00:00Z",
  "turnDeadline": "2026-09-20T12:01:30Z",
  "state": { "...": "PlayerGameState for recipient only" }
}
```

Клиент заменяет локальный снимок только сообщением с версией больше сохранённой.
Пропуск версии допустим, поскольку `state` — полный снимок. После принятой
команды собственный `StateUpdate` является подтверждением её результата;
клиент не применяет оптимистично вычисленный результат.

Перед **каждой** отправкой сервер обязан получить сетевое состояние так:

```text
playerState = projectFor(fullGameState, recipient.playerId)
wireState   = serializeNetworkProjection(playerState, recipient.playerId)
send(StateUpdate(state: wireState))
```

Нельзя сериализовать `GameState`, кэш полного состояния, объект колоды или
результат `projectFor` универсальным рефлексивным сериализатором. Разрешён только
явный allow-list сериализатора `serializeNetworkProjection`, покрытый тестами
на отсутствие секретных полей.

`PlayerGameState` на проводе содержит только:

- открытые `HexTile`; закрытая клетка передаётся лишь как `{q, r, isFogged:true}`
  без `id`, типа, выходов, вентиляции, терминала, `locationId` и любых объектов;
- видимые позиции, здоровье/урон, экипировку и общедоступные маркеры персонажей;
  карты рюкзака, модификации, состояния и личные задачи видит только их владелец;
  для остальных разрешены только числовые счётчики скрытых карт;
- видимых монстров, жетоны и открытые сюжетные задания;
- для каждой колоды только число оставшихся и, при необходимости, число сброса;
  никогда `drawPile`, `discardPile`, их порядок, идентификаторы будущих карт или
  данные, из которых они восстанавливаются;
- лишь решение, предназначенное получателю. Для остальных игроков pending-решение
  представляется как `{ "awaitingPlayerId": "…", "kind": "hidden" }`, без
  вариантов, кубиков, скрытых карт и контекста.

Секретны также серверный seed, состояние PRNG, необработанные события, резерв
героев до его раскрытия, внутренние курсоры и журналы с внутренними
идентификаторами. Их нет в `wireState`. Если тип `PlayerGameState` содержит
`seed` для офлайн-режима, сетевой сериализатор обязан исключить его; иначе seed
может позволить восстановить порядок детерминированно перемешанной колоды.

Эти правила означают именно границу передачи данных, а не запрет в интерфейсе:
клиент не получает закрытые комнаты или порядок колоды физически, поэтому не
может извлечь их мапхаком из памяти, сетевого лога или предзагруженных ассетов.
Пакеты контента с закрытыми карточками также не должны доставляться клиенту до
раскрытия, если их метаданные выдают порядок или расположение.

## Отказы и восстановление синхронизации

### `RejectionNotice`

Отказ не изменяет полный `GameState` и не увеличивает `stateVersion`:

```json
{
  "protocolVersion": 1,
  "roomId": "r-7f",
  "commandId": "8a0c2d9e-0db4-4a8c-b982-91306c02e35c",
  "code": "stale_state_version",
  "messageKey": "online.rejection.staleStateVersion",
  "currentStateVersion": 13,
  "retryable": true
}
```

Стандартные `code`: `stale_state_version`, `not_room_member`,
`not_current_controller`, `room_not_in_game`, `invalid_command`,
`command_id_reused`, `not_enough_actions`, `invalid_target_coord`,
`port_mismatch`, `path_blocked`, `target_out_of_range`,
`pending_decision_required`, `action_unavailable_in_phase`, `game_completed`,
`inventory_rejected`, `terminal_unavailable`, `chest_unavailable` и
`exchange_unavailable`. Сервер может добавить машиночитаемые поля, но не включает
в отказ скрытую информацию. При `stale_state_version` он сразу после уведомления
отправляет этому соединению актуальный `StateUpdate`; клиент строит новое
намерение только на его основе.

## Разрывы связи, таймеры и делегирование

### `PlayerDisconnected`

При закрытии или тайм-ауте сокета сервер помечает участника `waitingForReconnect`
и рассылает остальным:

```json
{
  "protocolVersion": 1,
  "roomId": "r-7f",
  "playerId": "p-ada",
  "status": "waitingForReconnect",
  "reconnectUntil": "2026-09-20T12:03:00Z"
}
```

Это сообщение не раскрывает `resumeToken`. При повторном входе `JoinRoom` сервер
публикует аналогичное presence-обновление со `status: "reconnected"` и отправляет
вернувшемуся его персональный снимок. Presence — служебное состояние комнаты и
может иметь отдельный `roomRevision`; оно не подменяет `stateVersion` игровой
партии.

В начале каждого хода сервер задаёт абсолютный `turnDeadline` на 90 секунд и
включает его в `StateUpdate`. Отсчёт не зависит от часов клиента и не
приостанавливается при разрыве. Новая команда активного контролёра до дедлайна
переносит тот же дедлайн только если команда по правилам завершила ход и открыла
следующий; иначе остаётся исходный дедлайн. Сервер обязан сам выполнить тайм-аут:

- если нет `PendingDecision`, он применяет серверную служебную команду
  `EndTurnCommand` за неответившего игрока;
- если ожидается выбор, сервер применяет документированный безопасный вариант:
  отказ от необязательного действия, `KeepRollChoice` для переброса и отсутствие
  уклонения там, где правило требует выбор. Для нового типа решения его
  безопасный дефолт должен быть задан в правилах до публикации;
- после тайм-аута меняется `GameState`, увеличивается `stateVersion` и все
  участники получают персональный `StateUpdate` с `reason: "turnTimedOut"`.

Окно ожидания переподключения равно 120 секунд от разрыва. Пока оно не истекло,
только прежний владелец через `resumeToken` управляет своим героем. До разрыва
владелец может через `SendCommand` типа `delegateControl` заранее указать одного
союзника. Это не команда редьюсера правил: она валидируется сервисом комнаты,
требует `expectedStateVersion`, согласия выбранного союзника и увеличивает
`stateVersion` как изменение прав управления. После истечения окна назначенный
союзник становится `controllerPlayerId` героя до отзыва владельцем после
переподключения. Только тогда его персональная проекция включает приватные карты
и решения делегированного героя; до передачи они остаются скрытыми.

Если делегат не назначен, герой остаётся в партии, а сервер продолжает завершать
его ходы тайм-аутом. Сервер не выбывает, не убивает и не заменяет персонажа из-за
одного сетевого разрыва. Владелец может отозвать делегирование после
переподключения через ту же версионную команду; сервер немедленно прекращает
выдачу его приватной проекции союзнику.

## Требования к реализации и проверке

- На сервере должна существовать ровно одна последовательная очередь переходов
  на `roomId`; параллельные команды не могут одновременно пройти одинаковую
  `expectedStateVersion`.
- Полное состояние, seed, PRNG и ключи дедупликации сохраняются транзакционно
  вместе с `stateVersion`, чтобы рестарт процесса не создавал двойной бросок или
  повторное взятие карты.
- Логи аудита хранят `roomId`, `playerId`, `commandId`, версию до/после и код
  результата, но не содержат секретные карты в незашифрованном виде.
- Контрактные тесты должны подтвердить идемпотентность повторного `commandId`,
  отказ устаревшей версии, строго последовательные версии и то, что разные
  получатели одной версии получают разные допустимые проекции.
- Отдельные negative-тесты сериализации должны искать в каждом исходящем пакете
  `drawPile`, `discardPile`, seed/PRNG, метаданные закрытых клеток, личные задачи
  других игроков, их скрытые карты и варианты чужого `PendingDecision`.
