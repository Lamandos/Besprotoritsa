# Фактический MVP-протокол онлайна

Этот документ описывает реализацию сервера на текущем этапе. Полная целевая
модель находится в [online-spec.md](online-spec.md); она не является обещанием
уже доступного JSON-RPC API.

## Создание и жизненный цикл

`POST /rooms` принимает только серверные параметры:

```json
{
  "contentSetId": "mvp",
  "partySize": 2,
  "mode": { "difficulty": "normal" }
}
```

Сервер загружает `content/mvp`, создаёт cryptographically secure seed и хранит
его вместе с отдельным состоянием PRNG. Нельзя передавать `GameState`, колоды,
карту, seed или идентификаторы героев. Нынешний доверенный набор `mvp` содержит
ровно двух героев, поэтому другие размеры партии отвергаются загрузчиком.

Создание ограничено десятью запросами в минуту на источник. У комнаты есть
лимит одновременных сокетов и 12-часовой TTL неактивности; истёкшая комната
архивируется в persistence и больше не принимает подключения.

## Подключение и токены

Клиент открывает `/rooms/<roomCode>/lobby/ws` или `/rooms/<roomCode>/ws` без
bearer-параметров в URL. Его первым сообщением является:

```json
{
  "type": "authenticate",
  "participantId": "player-…",
  "reconnectToken": "только при переподключении"
}
```

Новый участник получает `reconnectToken` в `joined`. Persistence хранит только
SHA-256 digest токена; исходный bearer token не попадает в snapshot или журнал.

## Состояние на проводе

`state.state` — версия `wireVersion: 1`, а не сериализованный `GameState`.
Обязательные верхнеуровневые поля включают `isComplete`; `quests.story` и
`quests.personal` содержат `{id,status}`. Личные задачи в `personal` получает
только владелец, другие участники видят лишь `hiddenPersonalTaskCounts`.

Клиент сначала валидирует `WireGameState`, после чего существующий MVP UI
использует только presentation adapter. Он не вызывает rules reducer и не
синтезирует результат команды. `seed`, PRNG, порядок колод, закрытые клетки,
чужие карты и чужие варианты решения не входят в wire-модель.

## Хранение

Снимок комнаты содержит состояние правил, ревизию, PRNG state, digest токенов и
журнал дедупликации команд. Полные снимки заменяются атомарно; журнал ограничен
по размеру. Каждая новая команда дополнительно попадает в append-only NDJSON
журнал через последовательную асинхронную очередь записи, поэтому обработчик
WebSocket не ждёт файловую операцию.
